# 智学伴第二阶段开发契约与协作规范

## 1. 使用范围

本文档用于本轮五人并行开发，目标是防止接口字段、权限、数据库和页面联调不一致。

本轮采用垂直功能分工，但所有模块必须遵守同一套公共契约。模块负责人可以独立完成页面和接口；涉及公共契约的变更必须先登记、再修改代码。

## 2. 契约优先原则

- 先确定接口契约，再写页面和 Service。
- 前端不能根据后端临时返回值自行猜字段。
- 后端不能为了迁就单个页面随意增加同义字段。
- 字段名称、类型、枚举和空值含义必须固定。
- 发现契约不足时，先在本文档新增或修改约定，并通知使用该接口的成员。
- 已经被其他模块使用的字段不允许直接改名；需要兼容时先保留旧字段，再约定删除时间。

## 3. 接口路径与归属

接口按业务功能划分，管理员接口统一使用 `/admin` 前缀：

| 功能 | 用户端接口范围 | 管理员端接口范围 | 负责人 |
| --- | --- | --- | --- |
| 账号与用户 | `/auth/*`、`/profile/*` | `/admin/users/*`、`/admin/auth/*` | 成员一 |
| 学情与统计 | `/mastery/*`、`/profile/diagnostic/*` | `/admin/dashboard/*` | 成员二 |
| 题目与练习 | `/learning/*`、`/questions/*` | `/admin/questions/*` | 成员三 |
| 错题与报告 | `/mistakes/*`、`/knowledge-reviews/*`、`/reports/*` | `/admin/learning/*` | 成员四 |
| VIP 与订单 | `/vip/*` | `/admin/orders/*`、`/admin/logs/*` | 成员五 |

新增接口命名规则：

- 查询集合使用复数名词，例如 `/admin/users`。
- 查询单个资源使用 `/{id}`，例如 `/admin/users/{user_id}`。
- 创建使用 `POST`，修改使用 `PUT` 或 `PATCH`，删除使用 `DELETE`。
- 状态动作使用明确动词，例如 `/admin/users/{id}/disable`。
- 不允许同一业务同时出现 `/user-list`、`/users/list` 等多个路径。

## 4. 统一响应格式

所有业务接口统一返回：

```json
{
  "code": "OK",
  "message": "success",
  "data": {}
}
```

成功但没有数据：

```json
{
  "code": "OK",
  "message": "操作成功",
  "data": null
}
```

失败响应：

```json
{
  "code": "USER_NOT_FOUND",
  "message": "用户不存在",
  "data": null
}
```

约定：

- `code` 使用大写英文和下划线。
- `message` 是可以直接展示给用户的中文说明，不能返回堆栈信息。
- 业务数据全部放在 `data` 中。
- 前端不得依赖 HTTP 状态码以外的非标准字段判断成功。
- 新增接口使用项目已有的 `success()` 和 `BusinessError`，不要自造响应格式。

## 5. HTTP 状态码

| 状态码 | 使用场景 |
| ---: | --- |
| 200 | 查询或写入成功 |
| 400 | 业务条件不满足 |
| 401 | 未登录、Token 无效或过期 |
| 403 | 已登录但没有权限或权益 |
| 404 | 当前权限范围内找不到资源 |
| 409 | 重复提交或状态冲突 |
| 422 | 请求字段校验失败 |
| 500 | 未预期的服务器错误 |
| 502/503 | 外部支付、AI 等依赖暂时不可用 |

权限错误不能返回 404 伪装成资源不存在；管理员接口被普通用户访问必须返回 403。

## 6. 认证、权限和数据隔离

普通用户接口和管理员接口都必须认证：

```http
Authorization: Bearer <access_token>
```

规则：

- 当前用户 ID 只能从 JWT 读取。
- 前端传入的 `user_id` 只能作为展示或筛选条件，不能作为授权依据。
- 普通用户只能查询和修改自己的数据。
- 管理员接口统一使用管理员权限依赖。
- 普通用户不得访问 `/admin/*`。
- 管理员的查看、禁用、补偿、修改等操作必须写审计日志。
- 支付回调不依赖用户登录，但必须验签并校验订单归属。

## 7. 请求字段与命名

- JSON 字段统一使用 `snake_case`，例如 `knowledge_point_name`。
- 数据库列名、Python 字典、Pydantic 模型和 API 字段保持同名。
- 前端可以使用 `camelCase` 的本地变量，但请求和响应转换必须集中在 API 层，不得一页一个规则。
- 布尔字段使用 `is_`、`has_` 或明确状态名，例如 `is_demo`、`is_read`。
- 时间字段使用 `_at`，日期字段使用 `_date`。
- 数量使用 `_count`，金额使用字符串传输，例如 `"19.90"`。
- ID 使用整数或字符串时必须在契约中固定，不能同一接口一会儿数字一会儿字符串。

## 8. 分页、筛选和排序

分页接口统一接收：

```text
page=1&page_size=20
```

限制：

- `page >= 1`。
- `1 <= page_size <= 100`。
- 默认按 `created_at desc` 或业务明确的时间倒序排列。
- 分页响应统一为：

```json
{
  "items": [],
  "page": 1,
  "page_size": 20,
  "total": 0,
  "pages": 0
}
```

筛选字段必须使用后端实际支持的字段；前端没有实现的筛选条件不得发送。

## 9. 时间、金额和枚举

### 9.1 时间

- API 时间使用带时区的 ISO 8601，例如 `2026-07-30T12:30:00+08:00`。
- 纯日期使用 `YYYY-MM-DD`。
- 业务日、每日次数和学习计划统一按 `Asia/Shanghai` 计算。
- 前端只负责展示，不重新计算业务日期。

### 9.2 金额

- 金额使用 `Decimal` 计算。
- JSON 中金额统一使用字符串，例如 `"19.90"`。
- 不使用浮点数判断支付金额是否相等。

### 9.3 公共枚举

数据库和 API 使用英文值，前端负责显示中文：

| 类型 | 枚举值 |
| --- | --- |
| 难度 | `easy`、`medium`、`hard` |
| 学习状态 | `weak`、`consolidating`、`mastered` |
| 错因 | `knowledge`、`calculation`、`reading`、`method` |
| 订单状态 | `pending`、`paying`、`paid`、`closed`、`refunded` |
| 复习模式 | `quick`、`full`、`advanced` |
| 数据来源 | `user`、`admin`、`simulation` |

未经确认不得新增同义枚举，例如不能同时使用 `completed` 和 `done` 表示同一个状态。

## 10. 写操作、幂等和事务

会产生以下变化的接口必须支持 `X-Request-ID`：

```http
X-Request-ID: <uuid>
```

适用范围：

- 答案提交。
- 错题订正。
- 复习完成。
- 积分变化。
- 订单创建。
- VIP 开通。
- 管理员补偿或批量操作。

相同用户、相同业务和相同 `request_id` 重复请求时，必须返回第一次处理结果，不能重复扣积分、增加 VIP 时长或更新掌握度。

涉及多张表的业务必须在一个事务中完成；失败时整体回滚。前端不能通过重复点击解决后端幂等问题。

## 11. 数据库与模型变更

- 每个成员只能直接维护自己功能归属的表和迁移脚本。
- 修改公共表前必须通知相关成员。
- 不允许在代码启动时静默删除表或清空数据。
- 新字段必须有默认值或兼容旧数据的处理。
- 外键、唯一索引和状态字段必须明确写入迁移脚本。
- 模拟数据必须带 `is_demo = true` 或 `simulation_batch_id`，不能与真实数据混淆。
- `reset_demo_data` 只能删除明确标记的演示数据。

## 12. 模块间数据事件

跨模块更新不要直接修改对方 Service 的内部对象。优先通过明确的方法或业务事件传递：

| 事件 | 产生模块 | 使用模块 |
| --- | --- | --- |
| `practice_completed` | 题目/练习 | 学情、错题、统计 |
| `mistake_created` | 题目/练习 | 错题、学情、统计 |
| `correction_completed` | 错题/复习 | 掌握度、积分、统计 |
| `review_completed` | 错题/复习 | 报告、统计、通知 |
| `order_paid` | VIP/订单 | 权益、用户、统计 |
| `admin_operation` | 任意管理员功能 | 日志 |

事件数据至少包含：

```json
{
  "event_type": "practice_completed",
  "user_id": 1,
  "source_id": 1001,
  "occurred_at": "2026-07-30T12:30:00+08:00",
  "request_id": "uuid"
}
```

## 13. 前端页面与接口约定

- 每个功能使用独立 API 文件和页面组件。
- 页面加载、空数据、加载失败、无权限和提交中状态必须明确处理。
- 表单提交按钮在请求期间必须禁用，防止重复提交。
- 前端不自行拼接业务统计结果，不自行改变订单或掌握度状态。
- 用户端和管理员端使用不同路由守卫。
- 管理员页面中的状态标签、金额和时间统一使用公共格式化方法。
- 接口字段变更后必须同步修改请求模型、响应模型、API 文件和测试。

## 14. Mock 与模拟数据规范

依赖模块未完成时，可以使用 Mock，但 Mock 必须遵循正式接口契约：

- Mock 字段名称、类型和枚举必须与正式接口一致。
- Mock 不得增加正式接口没有的临时字段。
- 接口完成后立即替换数据来源，不保留两套业务逻辑。
- 模拟数据统一由成员五生成和清理。
- 模拟数据脚本使用固定随机种子，保证演示数据可重复。

## 15. Git、提交和合并规则

分支命名建议：

```text
feature/member1-account
feature/member2-dashboard
feature/member3-practice
feature/member4-review
feature/member5-payment-integration
```

提交要求：

- 一次提交只完成一个明确功能。
- 提交信息说明模块和动作，例如 `feat(review): complete review card API`。
- 不提交密钥、真实账号、临时数据库导出和大体积构建产物。
- 不在自己的功能分支上直接重置或覆盖他人的修改。
- 合并前必须解决冲突，并说明是否涉及公共文件。
- 修改公共文件前先通知全组，并尽量拆成独立小提交。

## 16. 接口变更流程

如果必须变更已经使用的接口：

1. 在本文档记录变更原因、旧字段、新字段和影响模块。
2. 通知接口提供者、接口使用者和成员五。
3. 优先新增兼容字段或新接口，不直接删除旧字段。
4. 同步修改前端 API 文件、后端 Schema 和测试。
5. 完成一次跨模块联调后再合并。

紧急修 Bug 也必须在提交说明中写清楚是否改变了契约。

## 17. 测试最低要求

每个模块至少包含：

- 正常成功流程。
- 未登录访问。
- 权限不足访问。
- 参数校验失败。
- 空数据和不存在资源。
- 重复提交或幂等。
- 依赖服务失败时的降级或错误响应。

最终必须通过以下跨模块流程：

```text
普通用户登录
→ 做题
→ 产生错题
→ 完成复习
→ 查看报告
→ 创建并查询 VIP 订单
→ 管理员查看用户、统计、题目、错题、订单和日志
```

## 18. 冲突处理原则

发生冲突时按以下优先级处理：

1. 数据安全、权限和支付正确性。
2. 本文档已冻结的公共接口契约。
3. 业务功能完整性。
4. 页面视觉和交互偏好。

无法自行判断时，先停止修改公共契约，列出冲突字段、影响模块和建议方案，由全组确认后再继续。
